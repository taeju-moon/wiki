# W5 미션 리포트 - NYC Yellow Taxi PySpark DataFrame 분석

## 1. 개요

`main.py`로 2026년 1월 NYC Yellow Taxi trip 데이터를 읽어 정제/집계하는 파이프라인을 만들었다.
목표는 결과값 자체보다 Spark DataFrame이 내부적으로 어떻게 동작하는지(Lazy Evaluation, 실행 계획,
Stage, cache)를 확인하는 것이다. local[*] 모드로 실행했고, Spark UI(localhost:4040)를 통해
Jobs / SQL / Storage 탭을 확인했다.

## 2. 데이터 로딩 및 스키마

`StructType`으로 스키마를 명시해서 읽었다. inferSchema를 쓰지 않았기 때문에 스캔 단계에서
타입 추론용 추가 pass가 발생하지 않는다.

```
root
 |-- VendorID: integer
 |-- tpep_pickup_datetime: timestamp
 |-- tpep_dropoff_datetime: timestamp
 |-- passenger_count: long
 |-- trip_distance: double
 |-- RatecodeID: long
 |-- store_and_fwd_flag: string
 |-- PULocationID: integer
 |-- DOLocationID: integer
 |-- payment_type: long
 |-- fare_amount: double
 ... (이하 요금 관련 컬럼)
```

## 3. 데이터 정제 결과

null 제거 + 이상치 필터(거리 0 이하/100마일 초과, 요금 0 이하, 승객 수 0 이하/6명 초과,
시간 역전) 적용 결과는 아래와 같다.

| 구분 | row 수 |
|---|---|
| 정제 전 | 3,724,889 |
| 정제 후 | 2,551,810 |
| 제거된 row | 1,173,079 |

정제 전/후 count()는 둘 다 action이라 매번 전체 parquet을 스캔한다. 특히 정제 전 count는
필터가 하나도 안 걸린 순수 스캔 비용이고, 정제 후 count는 cache를 채우는 역할도 겸했다.

## 4. Lazy Evaluation 확인

`lazy_demo_df`를 filter → withColumn(trip_duration_minutes) → groupBy로 체이닝한 뒤
action 없이 `explain(True)`부터 호출했다. 이 시점 Jobs 탭에는 아무 Job도 없었다.
그다음 `count()`를 호출하자 그제서야 Job이 하나 생겼다. explain 시점과 count 호출 시점이
코드상 분리돼 있고, 로그도 "아직 action을 호출하지 않았다" → "Job 생성됨"으로 명확히 구분된다.

Optimized Logical Plan을 보면 filter 여러 개가 하나의 조건으로 합쳐지고, Physical Plan의
FileScan 노드에 `PushedFilters: [IsNotNull(trip_distance), IsNotNull(fare_amount), ...]`가
찍혀서 filter가 스캔 단계까지 내려간(predicate pushdown) 걸 확인했다.

## 5. Transformations

- **Filtering**: `passenger_count > 1` 합승 트립만 뽑은 `shared_ride_df`를 정의했다.
- **Aggregation**: 일자별(트립 수/평균 거리/총 매출) 집계와, 시간대별 평균 거리 집계를 만들었다.
  시간대별 집계에서 출퇴근 시간(7~9시, 16~19시)과 그 외 시간을 `is_commute_hour`로 구분했다.

| pickup_hour | is_commute_hour | trip_count | avg_trip_distance |
|---|---|---|---|
| 7 | true | 120,472 | 3.71 |
| 8 | true | 86,235 | 4.16 |
| 13 | false | 12,511 | 4.88 |
| 14 | false | 16,357 | 6.74 |
| 18 | true | 110,979 | 3.26 |

출퇴근 시간대라고 거리가 특별히 더 길거나 짧지는 않았고, 오히려 낮 시간(13~15시)에
장거리(공항 왕복 등으로 추정) 트립 비중이 높게 나왔다.

- **Join**: `taxi_zone_lookup.csv`(265 row짜리 작은 테이블)를 `broadcast()`로 감싸서
  PULocationID = LocationID로 join했다. 작은 테이블을 셔플 없이 전체 executor에 복제해서
  맵사이드에서 join을 끝내기 위함이다.

## 6. Broadcast Join DAG 확인

SQL 탭에서 join이 포함된 count 쿼리를 열어 DAG를 확인했다. 아래는 실행 중 캡처한 SQL/DataFrame
탭 목록 화면이다 (Completed Queries 13개, 전부 `count at NativeMethodAccessorImpl.java:0`로
찍혀서 이름만으로는 구분이 안 되고, 4개씩 묶어서 마지막 것이 join 쿼리였다).

![Broadcast Join DAG](DAG.png)

해당 쿼리를 열어보면 Physical Plan에 아래처럼 나온다.

```
BroadcastHashJoin [PULocationID], [LocationID], Inner, BuildRight, false
:- InMemoryTableScan [PULocationID, fare_amount]   <- cache된 cleaned_df
:     +- ... FileScan parquet ... PushedFilters: [...]
+- BroadcastExchange HashedRelationBroadcastMode(...)
      +- FileScan csv [LocationID, Borough] ... PushedFilters: [IsNotNull(LocationID)]
```

큰 쪽(taxi 데이터)에는 `Exchange`(셔플)가 없고, 작은 쪽(zone lookup)만
`BroadcastExchange`로 복제된 걸 확인했다. `broadcast()`를 빼고 같은 join을 돌리면
`SortMergeJoin` + 양쪽에 `Exchange` 노드가 추가로 붙는데, 이번엔 별도로 돌려보진 않았다.

## 7. Cache 전/후 실행 시간 비교

`--compare-cache` 옵션으로 같은 로직(filtering count + daily_agg count + hourly_agg count +
join count)을 cache 없는 cleaned_df와 cache 있는 cleaned_df에 각각 돌려서 비교했다.

```
[CACHE 없음] filtering+aggregation(x2)+join 실행 소요 시간: 1.15초
[CACHE 있음] filtering+aggregation(x2)+join 실행 소요 시간: 0.87초
[비교 결과] CACHE 없음: 1.15초 vs CACHE 있음: 0.87초 -> 1.32배 차이
```

캐시 있는 쪽이 더 빠르긴 했는데, 로컬 환경+작은 데이터라 차이가 드라마틱하진 않았다.
캐시가 없으면 매 count()마다 read+filter 체인을 처음부터 다시 실행하기 때문에,
데이터가 더 크거나 클러스터 환경이었으면 차이가 더 벌어졌을 것으로 예상한다.

Storage 탭에서는 `cleaned_df`가 `Disk Memory Deserialized` 형태로 캐시된 것과
파티션 수를 확인했다.

## 8. 정리

- explain()과 action 호출 시점을 코드로 분리해서 Lazy Evaluation을 직접 확인했다.
- predicate pushdown, broadcast join이 Physical Plan / DAG에 실제로 반영되는 걸 확인했다.
- cache는 효과가 있었지만 로컬 소규모 데이터라 체감 차이는 크지 않았다.
