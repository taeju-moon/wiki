# W5 미션 리포트 - NYC Taxi Trip Data 분석 (PySpark RDD API)

## 1. 학습 목표

Apache Spark의 내부 동작 방식(RDD, DAG, Lazy Evaluation)을 이해하기 위해, NYC TLC(Taxi and Limousine Commission) Trip Record Data를 PySpark RDD API로 분석하는 애플리케이션을 개발했다. DataFrame API 대신 RDD API의 transformation/action, narrow/wide 연산, Stage 분리를 직접 관찰하는 것을 목표로 했다.

## 2. 데이터셋

NYC TLC Trip Record Data 중 Yellow Taxi 2026년 1월 데이터(`yellow_tripdata_2026-01.parquet`)를 사용했다. 약 372만 건의 트립 레코드가 담겨 있다.

## 3. 기능 요구사항 구현 내용

### 3-1. Data Loading (`data_loader.py`)
`load_data(spark, path, file_format)` 함수를 구현했다. CSV/Parquet 두 포맷을 모두 지원하며, 파일을 읽은 뒤 곧바로 `.rdd`로 변환해 RDD를 반환한다. 지원하지 않는 포맷이나 존재하지 않는 경로가 들어오면 명확한 에러 메시지와 함께 예외를 발생시키도록 처리했다.

### 3-2. Data Cleaning (`data_cleaner.py`)
`parse_and_validate(row)`로 각 row를 파싱/검증하고, `clean_data(rdd)`로 결측치·타입 오류가 있는 row를 제거했다. pickup_datetime, fare_amount, trip_distance, passenger_count 컬럼을 확인해서 값이 없거나(KeyError) 타입 변환이 실패하면(ValueError/TypeError) 해당 row를 버리도록 구현했다. 정제 전/후 row 개수와 제거 비율을 로그로 남긴다.

### 3-3. Transformation Logic (`data_transformer.py`)
다음 순서로 transformation을 체이닝했다.
1. `filter_valid_fares`: fare_amount > 0인 row만 남긴다. (narrow, 셔플 없음)
2. `map_to_daily_keyvalue`: `(date, (fare, distance, 1))` 형태로 변환한다. (narrow)
3. `reduce_by_date`: `reduceByKey`로 날짜별 fare/distance/count 합계를 구한다. (wide, 셔플 발생)
4. `compute_totals`: `reduce` 액션으로 전체 총 매출/거리/트립 수를 계산한다.

groupByKey 대신 reduceByKey를 사용해서 파티션 내 map-side combine으로 셔플되는 데이터량을 줄였다.

### 3-4. Aggregation Logic (`result_aggregator.py`)
- `build_summary`: 총 트립 수, 총 매출, 평균 이동 거리를 계산한다.
- `format_daily_metrics`: 날짜별 트립 수/매출을 `sortByKey`로 날짜 오름차순 정렬한다.
- `print_report`: 콘솔에 전체 요약과 일별 지표(상위 10일)를 출력한다.

### 3-5. Performance Optimization
- 여러 액션에서 재사용되는 RDD(`rdd`, `cleaned_rdd`, `filtered_rdd`, `daily_metrics_rdd`)는 `persist(StorageLevel.MEMORY_AND_DISK)` 또는 `cache()`로 캐싱해서 동일 lineage가 중복 계산되지 않도록 했다.
- 더 이상 필요 없어진 RDD는 `unpersist()`로 즉시 메모리를 반환하도록 했다.
- 로컬 코어 수(`os.cpu_count()`) 기준으로 파티션 수를 자동 조정하는 로직을 추가했다.
- DataFrame 변환 시 명시적 스키마(StructType)를 지정해서 Spark가 타입을 추론하기 위한 불필요한 액션이 발생하지 않도록 했다.

### 3-6. Result Storage
`save_results`로 summary와 daily_metrics를 각각 `{output_path}/summary.{csv|parquet}`, `{output_path}/daily_metrics.{csv|parquet}` 경로에 저장한다. `--output-format`으로 csv/parquet을 선택할 수 있다.

## 4. 프로그래밍 요구사항 구현 내용

- Python으로 Spark 애플리케이션을 작성했고, 전 구간에서 RDD API를 사용했다 (DataFrame API는 파일 로딩/저장 시에만 최소한으로 사용).
- 최소 5개 이상의 transformation을 사용했다: `map`(parse_and_validate), `filter`(정제), `filter`(유효 fare), `map`(daily keyvalue), `reduceByKey`, `map`(daily metrics 변환), `sortByKey`, `map`(최종 포맷 변환).
- 집계 지표(총 트립 수, 총 매출, 평균 거리, 일별 트립 수, 일별 매출)를 모두 계산해서 출력한다.
- 결과를 로컬 파일 시스템에 CSV/Parquet으로 저장한다.

## 5. 실행 방법

```bash
cd missions/W5
pip install -r requirements.txt

python3 main.py \
  --input-path ./yellow_tripdata_2026-01.parquet \
  --input-format parquet \
  --output-path ./output \
  --output-format csv \
  --keep-alive
```

`--keep-alive`를 붙이면 파이프라인 종료 후 Enter를 누르기 전까지 SparkSession이 살아있어서, 그동안 `http://localhost:4040`에서 Spark UI(Jobs/Stages/DAG)를 확인할 수 있다.

## 7. 트러블슈팅: data_cleaner.py Stage가 느린 문제

### 증상
Spark UI에서 확인한 결과(위 스크린샷), `data_cleaner.py:192`의 `count()`(정제 후 count, 즉 `parse_and_validate` map + filter를 포함한 lineage)가 **1.5분**이 걸린 반면, `data_cleaner.py:184`의 `count()`(정제 전 count, 원본 rdd 그대로)는 8초밖에 걸리지 않았다. 즉 병목은 `parse_and_validate`가 적용되는 map 단계에 있었다.

### 원인 진단
1. **파티션 수**: 원본 parquet 파일의 파티션 수(10개)와 로컬 코어 수(10개)가 같아서, 파티션 수 자체는 큰 병목이 아니었다.
2. **strptime 비용**: `datetime.strptime()`을 문자열 슬라이싱으로 바꿔서 1,000,000 row 샘플로 벤치마크했지만, 실제로는 52.03초 → 52.74초로 유의미한 차이가 없었다. 즉 날짜 파싱 방식 자체는 병목의 핵심 원인이 아니었다.
3. **결론**: 진짜 병목은 RDD API 특성상 각 row(pyspark.sql.Row)를 JVM ↔ Python 프로세스 간에 직렬화/역직렬화하면서 Python 함수(`parse_and_validate`)를 row 단위로 실행하는 오버헤드였다. 372만 건의 row를 한 건씩 Python 워커로 넘겨 처리하는 구조 자체가 느릴 수밖에 없고, 이는 RDD API를 써야 하는 과제 특성상 구조적으로 발생하는 비용이다.

### 조치한 개선 사항
- `parse_and_validate`의 예외 처리 범위를 좁히고(컬럼 조회는 KeyError만, 타입 변환은 ValueError/TypeError만), 날짜 파싱은 문자열 슬라이싱으로 단순화해서 함수 자체의 오버헤드를 최소화했다.
- `rdd`, `cleaned_rdd`를 `persist(StorageLevel.MEMORY_AND_DISK)`로 캐싱해서 정제 전/후 count가 lineage를 중복 계산하지 않도록 했고, 더 이상 쓰이지 않는 시점에 `unpersist()`로 메모리를 반환했다.
- 로컬 코어 수 기준 파티션 자동 조정 로직(`_adjust_partitions`)을 추가해서, 파티션이 코어 수보다 적은 환경에서는 병렬성을 높이도록 대비했다 (이번 데이터셋 기준으로는 이미 파티션 수가 적절해서 실질적인 조정은 발생하지 않았다).
- 파이프라인 종료 후 `--keep-alive` 옵션으로 SparkSession을 유지해서, Spark UI가 종료되지 않고 Stage/DAG를 확인할 수 있도록 했다.
